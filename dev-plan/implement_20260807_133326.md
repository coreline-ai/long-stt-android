## 개발 목적
6시간 전사 결과를 잃지 않고 조회·삭제할 수 있게 하고, 오디오와 Whisper 모델을 앱 안에서 지속적으로 선택·관리한다. 전사 시작 전 청크 계획과 실행 중 디코딩·STT·저장·냉각·재개 상태를 사용자가 사실대로 확인할 수 있는 장시간 전사 모니터를 제공한다.

## 개발 범위
세션 기반 전사 결과 보관함, 결과·오디오·모델 삭제, 설치 모델 전환/다운로드, 이전에 가져온 오디오 목록과 재선택 UI를 구현한다. 메인 화면은 6시간 단일 오디오 전사 흐름으로 단순화하고, CSV는 텍스트 결과가 아닌 별도 성능 기록으로 분리한다. 전사 준비 화면에는 예상 청크 수·시간 범위·냉각 계획을 표시하고, 실행 화면에는 완료 청크 기준 전체 진행률, 현재 작업 단계, 청크 상태 지도, 마지막 안전 저장 지점, 냉각 카운트다운과 재개·실패 상태를 표시한다. 모든 파일 조작은 활성 전사 세션과 분리하고 앱 내부 저장소에서 원자적으로 수행한다.

## 제외 범위

## Phase 6. 진행 상태 계약·전사 시작 전 계획 표시

### 목표
- Service가 실제 처리 상태를 문자열이 아닌 구조화된 경량 상태로 제공하고, 실행 전에는 선택한 음원의 청크 구성과 냉각 계획을 정확히 미리 보여준다.

### 책임 단위와 경계
- `TranscriptionPlan`: 청크 수·기본/디코드 범위·예정 냉각 시간을 계산하는 단일 기준이다. UI가 Service 상수를 복제하지 않는다.
- `TranscriptionProgressSnapshot`: 현재 단계와 저장 완료 상태만 전달한다. 전사 전문이나 전체 checkpoint JSON은 Intent에 넣지 않는다.
- `TranscriptionService`: 실제 단계와 시간을 생성한다. UI 문구를 추론하지 않는다.
- `SttViewModel`: Service 상태를 화면 상태로 변환하고 Activity 재생성 시 마지막 snapshot/checkpoint를 결합한다.

### 구현 태스크
- [ ] 10분 청크·앞뒤 1초 overlap·5청크마다 30초/그 외 10초 냉각 계산을 `TranscriptionPlan`으로 공통화한다.
- [ ] 정확한 음원 길이에서 `totalChunks`, 마지막 기본 구간, 디코드 구간, 총 냉각 시간을 계산한다.
- [ ] 진행 단계를 `PREPARING/LOADING_MODEL/DECODING/TRANSCRIBING/SAVING/COOLING/VERIFYING/COMPLETED/FAILED`로 정의한다.
- [ ] snapshot에 sessionId, 단계, 현재/전체/완료 청크, 기본·디코드 시간 범위, 시도 횟수, 단계 시작시각, 마지막 저장 청크·시각·글자 수, 냉각 종료시각을 포함한다.
- [ ] 기존 Service 상태 broadcast를 구조화하되 기존 status/progress extra 호환을 유지한다.
